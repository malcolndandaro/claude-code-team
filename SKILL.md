# /team — agent team emulation

**If the arguments are empty or are exactly `--help`:** print `~/.claude/skills/team/HELP.md` to the user verbatim (as markdown) and stop — do not start a team.

You are the **lead**. Each teammate is a separate interactive `claude` session in its own pane — a split of the lead's tab in cmux or ArcaTerm (`--tabs`: one tab each instead) — named and titled `<team>-<role>` (the title stays fixed so the user can manage panes; in ArcaTerm only `--tabs` tabs carry it), reachable with SendMessage. Teammates can message each other directly. Defaults: 3 roles, 1 challenge round; the lead fits a model to each role (`--model` forces one everywhere; see `--help`). `--inline` runs teammates as in-session named subagents instead (no panes, no cmux or ArcaTerm required; see the end). Pane modes need cmux or ArcaTerm, whichever pane you run in (`team.sh` picks it; see `--help`) — if neither is present, fail fast with an install hint (https://cmux.dev).

## 0. Workspace
Pick a short team slug (e.g. `rev1`) and run `bash ~/.claude/skills/team/team.sh init <team>` from the working directory. It creates/keeps `.team/` at the project root (git root, else cwd), adds `.team/` and `CLAUDE.local.md` to `.gitignore` in a git repo, adds a pointer note to `CLAUDE.local.md` once, and prints this run's dir `<run>` (`.team/runs/<date>-<team>/`).

**Close earlier-run leftovers** (skip this step when `--inline`). Run `bash ~/.claude/skills/team/team.sh reap --exclude <team>` — it lists live teammates from earlier runs of this project scoped to this project's root. Any row dated today is flagged "(run started today: may be live in another lead session)" — treat those with caution. Registries with no project root are summarised as a single "N live teammate(s)…left alone" line and are never closed by `--yes`. If the list has closeable rows, use AskUserQuestion with first option "Close the listed teammates (Recommended)" and second "Skip, leave them running"; caution the user if any row is dated today. On confirm, run `bash ~/.claude/skills/team/team.sh reap --yes --exclude <team>`. If reap prints "no live teammates left", skip the question.

**Name the lead workspace** (skip under `--inline` when neither cmux nor ArcaTerm is present). Run `bash ~/.claude/skills/team/team.sh lead-title` — it sets the cmux workspace and tab title (in ArcaTerm, the tab title) to `Main Board - <project>` and prints the title. The Claude session name is set at launch with `claude --name "Main Board - <project>"` and cannot be changed non-interactively; if the session was started without `--name`, use AskUserQuestion with first option "Done — I typed `/rename <printed title>` in this pane (Recommended)" and second "Skip" to ask the user to rename it now. After the user responds, run ListAgents and capture whatever name appears on the "This session is…" line as `<lead>` (if any other session row shares that display name, also note the ` [ref]` suffix). **Do this before spawning** — every teammate's prompt hard-codes `<lead>`.

**Continue workspace setup.** Read `.team/facts.md`. Run `bash ~/.claude/skills/team/team.sh roles` to list the roles available here (project roles override shared roles).

**Run type.** With `--tickets [slug]`, or a task that asks to implement tickets (a `.scratch/<slug>/issues/` feature, tracker issues labelled ready-for-agent), this is a **ticket run** — follow "Ticket runs" below instead of steps 1–4. A task that asks to *build a feature* in a git repo is offered as one too: in step 1, use AskUserQuestion with first option "Plan it as tickets and implement them in parallel (Recommended)" and second "Build run with lens roles". If the task edits code *and* the project is a git repo, this is a **build run**: every teammate works like a separate person — its own git worktree `.team/worktrees/<team>-<role>` on branch `team/<team>-<role>`, its own commits, and (unless `--no-gate`) its own **no-mistakes** gate run that reviews/tests/lints, pushes the branch, and opens a PR. Otherwise (read-only task, or not a git repo) it's a **review run**: no worktrees, no gate; editing roles get exclusive files instead.

## 1. Understand the task first (always)
**Never spawn teammates straight from the task text.** A wrong assumption here gets paid once per teammate, so resolve it before there are N of them.
- **Grill the task with the user.** Invoke the `grill-with-docs` skill when the run builds something in a git repo (it runs `grilling` and records the glossary and ADRs as decisions settle), else `grilling`. Work its design tree in rounds — intended outcome, who it is for, what success looks like — but put every round to the user through AskUserQuestion (up to 4 questions per call, your recommended answer first, labelled "(Recommended)"): this skill's AskUserQuestion rule wins over grilling's prose format. Facts are yours to find (dispatch a subagent); decisions are the user's. If the Skill tool refuses one of these skills (model invocation disabled), ask the user to type the slash command and continue after it. The task line is a starting point, not a brief.
- **Re-read the previous input.** What the user said earlier in this conversation — corrections, preferences, and anything they asked for that is still outstanding — plus `.team/facts.md` and the most recent `.team/runs/*/synthesis.md`. State which of it you are carrying forward so a wrong reading gets corrected now.
- **Ask every question that changes the work.** Use AskUserQuestion (up to 4 questions at once, recommended option first labeled "(Recommended)") and keep asking until nothing material is unresolved: scope and non-goals, which files are in play, what "done" means, how the result gets verified, and anything ambiguous in the task. Prefer asking over assuming.
- **Get the plan approved.** Write back the task as you now understand it, the roles and their lenses, what is out of scope, and how the result will be verified. Use AskUserQuestion with the first option "Proceed with this plan (Recommended)" and wait for the user's explicit approval before spawning — every run, not just `--autoroles`.

## 2. Plan the team
- **If the user listed roles in the task, use exactly those.** For a bare name, run `bash ~/.claude/skills/team/team.sh role <name>` — it prints the spec path (project `.team/roles/` first, then the shared library `~/.claude/team/roles/`), or exits 3 when there is none; then treat the name as a new role.
- Otherwise, with `--autoroles`, do a quick, cheap scan (a few commands, no deep reads; never print secrets or data files): CLAUDE.md / README, top-level layout and languages, test and CI setup, `git status` / `git diff --stat` / recent `git log` if it's a repo, and stack markers (`databricks.yml`, notebooks, `pyproject.toml`, `package.json`, Dockerfiles). **Prefer roles from `team.sh roles`** that fit; invent new roles only for uncovered lenses (e.g. diff spanning `src/api` + `src/ui` → `backend` + `frontend`; bundle + notebooks → `dabs-config` + `pipeline-logic`; missing tests → `tests`). Show the roster as a table (role · lens · owns · one-line *why* citing the file/signal, marking each role project / shared / new) and wait for the user's OK or edits before spawning (use AskUserQuestion, first option "Approve this roster (Recommended)").
- Without either, pick a small number of roles (2–3 is usually right) from the task text.
- Each role: kebab-case name, one lens, and — if the task edits code — an **exclusive set of files**. Never let two roles edit the same file. Research/review/debug: include one adversarial role.
- **Pick a model per role: opus or sonnet, nothing else.** `bash ~/.claude/skills/team/team.sh models` lists what is offered here (org-managed, read at run time; only opus- and sonnet-tier models are offered, and spawn refuses anything else, haiku-tier ids such as GLM / Kimi included). Get each id with `team.sh pick-model opus|sonnet` rather than hard-coding it. **Ticket implementers get sonnet; every other role gets opus** — reviewers, the adversarial role, researchers, build-run roles. A role spec's **Preferred tier** or a stated reason in the roster can move a role to the other tier; `--model` forces one model for every teammate. **Always pass a model** — without one, spawn uses the newest opus; `team.sh list` shows what each teammate is actually running. **Spawn teammates sequentially** — each spawn appends to the shared registry, and parallel spawns can over-count the cap.
- Save each new approved role to `.team/roles/<role>.md` under five headings — **Lens** · **Typical scope** · **Constraints** · **Preferred tier** (opus/sonnet, *not* a model id — ids go stale) · **Lessons** (empty at first; filled in step 5). A role describes *how to work*, never facts about a project — facts go only in `.team/facts.md`. Don't overwrite an existing spec unless the user asks.
- Write `<run>/tasks.md`: one line per role (`- [ ] <team>-<role>: <scope> — owns: <files or "read-only"> — model: <model> — spec: <path from team.sh role, or "new">`), so the run record shows what each role ran on.
- Run ListAgents once and note this session's own name (the "This session is …" line) — that is `<lead>`. If any other session row shares the same display name, also capture the ` [ref]` suffix and use `<name> [<ref>]` as `<lead>` in all prompts to keep SendMessage unambiguous.
- Show the roster in one short table, including each role's model and why that tier; spawning waits for the step-1 approval in every run. **Build run with gate:** the roster must say that each teammate will push `team/<team>-<role>` and open a PR, and you must use AskUserQuestion (first option "Spawn and run (Recommended)") before spawning (it publishes to the remote). Then run `bash ~/.claude/skills/team/team.sh gate-init` once from the repo: it sets up the no-mistakes gate (adds a local `no-mistakes` git remote). Exit code 3 = gate unavailable (not installed or no `origin`) — tell the user and continue as a build run without the gate.

## 3. Spawn (one pane per role)
For each role, write its prompt to `<run>/prompts/<role>.md`, then run from the working directory:
`bash ~/.claude/skills/team/team.sh spawn [--tabs] [--worktree] [--no-caveman] <team> <role> <run>/prompts/<role>.md <model>`
(`--worktree` for every build-run teammate; `--tabs` / `--no-caveman` only if the user gave them). Teammates start in auto permission mode, with a fixed pane/tab title, with `teammate-rules.md` appended to their system prompt (split independent work across subagents in one message; verify what comes back), and with the caveman terse-output style unless `--no-caveman`. Those two are concatenated into one appended file because `claude` keeps only the last `--append-system-prompt-file`. The script prints where the pane/tab opened.

After each spawn, run `bash ~/.claude/skills/team/team.sh sync <team>` — this updates the lead workspace sidebar with current progress (spawning N/M, phase).

Each prompt must be self-contained (teammates don't see this conversation) and include: goal, lens (copied from the resolved role file if one exists), files owned / readable, constraints, the roster (all `<team>-<role>` names), and these instructions:
- "You are `<team>-<role>` on a team led by `<lead>`. Use exactly `<lead>` (including any ` [ref]` suffix if shown) as your SendMessage `to:` target for the lead. You may message teammates directly with SendMessage (use ListAgents if a name doesn't resolve)."
- "Dispatch at most 4 concurrent subagents per message: whenever you have 2+ independent sub-tasks (exploring areas, reviewing files, running checks, drafting separate pieces), dispatch them with the Agent tool in a single message — up to 4 at once. A 5th concurrent Agent call fails at launch with 'Concurrent subagent limit reached'; it never runs, so for more than 4 dispatch in batches of 4, wait for all 4 to return, then dispatch the next batch. Verify that every subagent you dispatched actually returned a notification before treating its work as done. Pass `model` on every subagent call — sonnet, or opus for judgment-heavy pieces; never a cheaper model. Keep your own context for coordination and verification. Do sequential work yourself only when steps depend on each other."
- "First read `<abs>/.team/facts.md`, then run `bash ~/.claude/skills/team/team.sh facts-lint` and re-check only the facts it marks CHECK / GONE / NOANCHOR (a FRESH fact's cited file is unchanged since its evidence SHA). Treat entries as leads, not ground truth; report any you find contradicted as STALE."
- "Write a one-line status update to `<abs run>/status/<role>.txt` at each major step (e.g. `investigating facts`, `drafting report`). `<role>` is the bare role name without the `<team>-` prefix — a teammate titled `rev3-docs` writes to `<abs run>/status/docs.txt`. Use the exact absolute path substituted in your prompt. Overwrite each time — do not append."
- Build run only: "You work in your own git worktree `<abs worktree>` on branch `team/<team>-<role>` — edit and commit only there (small, focused commits; never touch other teammates' worktrees or the main checkout). Stay inside your scope so your PR doesn't conflict with teammates'. When your work is committed and verified, gate it: `no-mistakes axi run --intent \"<your goal in one sentence>\"` (never `--yes`). At each approval point: `no-mistakes axi respond --action fix` for actionable findings; send `NEEDS INPUT` to the lead for judgment calls, protected-path or unvalidated-test refusals — never approve those yourself and never ask in this pane. If `--wait` elapses, reattach with `no-mistakes axi status`. Include your branch, the gate outcome, and the PR URL in your report." (If the gate is off, replace the gate part with: "leave your commits on the branch; don't push.")
- "When done, write your report to `<abs run>/reports/<role>.md`, tick your line in `<abs run>/tasks.md`, then SendMessage the same report to `<lead>`, then wait for further messages. Format:"
```
FINDINGS: numbered, each with evidence (file:line, command output, or source)
CONFIDENCE: high/medium/low per finding
STALE FACTS: facts.md entries contradicted, with evidence (or "none")
OPEN QUESTIONS: what you couldn't verify
PARALLELISM: how many subagents you dispatched and for what (or why the work was not splittable)
```
After spawning all teammates, run `bash ~/.claude/skills/team/team.sh sync <team>` to set the sidebar to the initial "spawning" phase, then run ListAgents to confirm every teammate appears (retry briefly; sessions take a few seconds to start). If one doesn't, read its screen with `cmux read-screen --surface <ref> --lines 30`, or in ArcaTerm `arcaterm pane dump --pane <ref> --scrollback --tail-lines 30` (the ref is in `/tmp/team-<team>.tabs`) to see why — e.g. a trust or permission prompt the user must answer in that pane — and tell the user. Unless `--no-monitor` was given, run `bash ~/.claude/skills/team/team.sh monitor <team>` after all teammates have spawned — it opens one auto-refreshing status pane (not a teammate; not counted toward the cap; closed with the team). A monitor that is already running is not an error. **Never run it under `--inline`**: no registry exists there, so the monitor and `team.sh status` exit 3.

**Panes are the user's audit view.** Teammates open in a two-column grid to the right of you, so each stays readable instead of getting 1/N of the screen height. A pane exists only while its teammate has work to do:
- When a teammate's report arrives, verify it, then `bash ~/.claude/skills/team/team.sh finish <team> <role>`. It marks the row finished (session id and cwd kept) and closes the pane. It refuses (exit 2, nothing changed) unless the report has more `PARALLELISM:` lines than when the session was spawned (a blockquoted peer trailer does not count), `tasks.md` has `- [x] <team>-<role>:`, and — on a build run — the worktree has no uncommitted changes (the close kills the session). Run `finish` only on receiving the report, never because a file appeared; each round's report must add its own `PARALLELISM:` line. Exit 1 means the close failed: re-run `finish`. Then run `team.sh sync <team>`.
- A finished teammate has no session and is not in ListAgents. Its report, `tasks.md` line and registry row are the record; do not SendMessage it (see step 4 for the next round).
- `... show <team> <role>` brings that teammate's pane to the front and focuses it (a `--tabs` teammate is first moved out of your pane into its own). It deliberately moves focus off you, which is the point when the user must approve a permission prompt there; exit 3 if the teammate is finished, gone or not recorded.
- `... list <team>` prints each teammate as working / tab / finished / dead / unknown — use it to reconcile instead of guessing.

## 4. Challenge rounds (default 1)
Before nudging a stalled teammate, run `team.sh status <team>` and read its STATE; rows under `NEEDS YOU` come first. If `waiting`, the teammate used AskUserQuestion (a rule violation — teammates must only use NEEDS INPUT); `team.sh show <team> <role>` it and SendMessage reminding it to send `NEEDS INPUT` to you instead. In ArcaTerm, `waiting` can also be a tool-permission prompt: `show` it first, tell the user to approve it there, and send the reminder only when its pane shows a question. If `dead`, respawn it; if `model gone`, the model it ran on is no longer available — respawn with a different model; `stalled?` means only "no status update in 10 minutes", not "stuck": a teammate inside a long hook or a subagent wait legitimately stops writing status lines, and a live false positive was seen this run. Look at its pane (`team.sh show <team> <role>`) before messaging it, since a message costs a working teammate context. If `unknown`, the teammate was opened in another terminal, or the terminal could not be queried, so its state cannot be read — check ListAgents. `idle` (turn ended, no report yet) is routine while it waits on a peer or on you and deliberately does not appear under `NEEDS YOU`; it becomes `stalled?` after 10 silent minutes. In cmux, a teammate blocked on a *tool-permission prompt* is a known blind spot: permission prompts create no notification row, so it shows `working` for 10 minutes and then `stalled?`. When a teammate has been silent that long, `team.sh show <team> <role>` it so the user can approve the prompt in its pane. Live teammates' state is read from the terminal — the hooks cmux injects, or ArcaTerm's agent status — not from their screens. A finished teammate has no surface, so its state comes from the report on disk and its registry row. Run `team.sh sync <team>` after receiving each report.

When all reports are in, every teammate is already finished (step 3 finishes it the moment its report arrives), so every later round **resumes** it: `bash ~/.claude/skills/team/team.sh spawn --resume <team> <role> <prompt-file> [model]` (same flags as a normal spawn, before `<team>`) continues its recorded session with full context, and `<prompt-file>` is the new instruction (for a challenge round, the other teammates' findings). Do not keep a reported teammate live to SendMessage in the next round: its round-2 append would have no baseline, so `finish` could close it mid-write. The cost is one resume spin-up per teammate per round instead of a cheap message; the gain is that a teammate exists only while it is working. SendMessage still applies to a teammate that has **not yet reported** (e.g. answering its NEEDS INPUT). A resumed session keeps its **round-1 system prompt**: edits to `teammate-rules.md` since then are silently ignored, so anything the resumed teammate must now do differently goes in `<prompt-file>`. If `--resume` exits 3 (no recorded session, or its directory is gone because `team.sh clean` removed the worktree), fall back to a plain `spawn` whose prompt tells it to read `<run>/reports/<role>.md` first. `close` drops finished rows and removes the registry, so after a formal shutdown there is no full-context resume; a later run can still spawn the role fresh and have it read its report, which stays in `.team/runs/`, but it will not carry the old conversation. Give each teammate, in its resume prompt, the *other* teammates' findings, labeled by name: "Try to disprove or refine these using evidence — message the author directly if useful; if the author is no longer listed in ListAgents (it finished), send it to `<lead>` instead. Then append your AGREE / DISPUTE (with evidence) / REFINE per finding and revised list to your report file, and send it to me." Resume all before waiting. Relay faithfully — never present your own claims as a teammate's.

## 5. Synthesize and record
Report: build runs first list each teammate's branch, gate outcome, and PR URL, and flag any teammates whose branches touch the same files (merge-conflict risk). Then **Consensus** (survived challenge, with evidence) · **Disputed** (each side's best evidence) · **Dropped** (refuted, one line each) · **Next steps**. Save the same text to `<run>/synthesis.md`.
Update `.team/facts.md`: append **consensus findings only** as one line each (`- <fact> — evidence: <file:line | command> @<git short SHA> — <YYYY-MM-DD>, run <run dir name>`; use `@nogit` outside a repo), and for each confirmed STALE fact, strike it through with a pointer to the contradicting run (don't delete). Before appending, write your new lines to a scratch file and run `bash ~/.claude/skills/team/team.sh facts-lint --pre-append <file>` — it refuses on a secret/PII hit. Never write secrets, PII, raw data, or unverified claims. Tell the user how many facts were added / marked stale.
Make roles learn: for each role spec used this run, first run `team.sh role-pull <name>` to pull any library updates before writing a lesson (exit 3 = project-only, nothing to pull, proceed; exit 5 = diverged or no base — show the user both diffs and never pass `--force` without their explicit OK, as force overwrites local lessons), then append at most one line under its `**Lessons:**` heading when the challenge round exposed a *method* failure — what the role missed and how to work next time (e.g. "reproduce shell claims in a scratch repo; doc-reading alone missed the bug"). Lessons are about method, never this project's code (that goes to facts.md); cap at ~8 lines and propose a merge when full. Show the user the diff before writing.
**Promote roles (optional).** Check `team.sh roles` for each project role used this run. For roles showing `local-ahead`, `diverged`, `diverged (no base)`, or `project-only`, use AskUserQuestion — batched up to 4 per call — question: "Promote `<role>` to your shared library (`~/.claude/team/roles/`)?"; first option: "Promote (Recommended)"; second: "Keep project-only". On yes: run `team.sh role-promote <name>` (it scans for secrets/PII, shows the diff, and copies it). For `global-ahead` roles (library is newer): tell the user to run `role-pull` first instead. For `library-only` (no project copy to promote) and `in-sync`: skip silently. Never git-commit the shared library (it lives outside any repo).
Every teammate has been finished (`team.sh finish <team> <role>`) as its report was verified (step 3), so the workspace ends with only the lead and the monitor; finish any that is still live. Run `team.sh sync <team>` after finishing. Unless `--autoclose` was given, in which case shut the team down right after this step. When the user says the team is done ("shut down the team"), SendMessage each still-live teammate that the team is done, then run `bash ~/.claude/skills/team/team.sh close <team>` (closes every recorded pane/tab; the run record in `.team/` stays) followed by `bash ~/.claude/skills/team/team.sh sync --clear <team>` to clear the sidebar pill. For build runs, also run `bash ~/.claude/skills/team/team.sh clean <team>` — removes worktrees without uncommitted changes (branches and PRs stay); report any it kept.

## Rules
- Don't do teammates' work yourself; wait for their messages. If one stalls, message it; if it died, respawn with the same name.
- A finished teammate is closed, not hidden: if one is needed again, resume it (step 4). If a *live* one goes quiet, `team.sh show <team> <role>` so the user can see whatever is waiting in it.
- Every claim in the synthesis and facts.md must trace to a teammate's evidence.
- Teammate *tool-permission* prompts (the CLI's approve-this-command modals) appear in *their* panes — tell the user to approve there; never relay approvals between sessions. (Agent *questions* are different — they are forwarded to you; see the next rule.)
- **Every question to the user goes through AskUserQuestion, with the recommended option FIRST and labelled "(Recommended)".** This covers: your own questions about scope or approach; relayed teammate NEEDS INPUT; gate judgment calls forwarded to you; the reap confirmation; the ticket queue approval; plan/roster approval; role promotion. Plain-text questions to the user are not allowed — always use AskUserQuestion.
- **Relay teammate questions to the user.** A teammate message whose first line is `NEEDS INPUT` is a question, not a report: present it to the user with AskUserQuestion, naming the asking teammate in the question text (the header is too short for the full `<team>-<role>` name), with the teammate's recommended option listed first and labelled "(Recommended)". Batch up to 4 pending questions into one AskUserQuestion. Then SendMessage the chosen answer back to that teammate. Do not `show` the teammate for this — the Q&A happens in your pane, which is the whole point. This keeps all input in one place instead of scattered across panes.
- Keep your own synthesis to the user in normal prose (caveman style is for teammates only).
- Cost: each teammate is a full session. Prefer fewer, sharper roles; a ticket run spends its parallelism on slices, not on extra roles.
- Reserved role names: `monitor` is reserved (collides with the status pane title `<team>-monitor`); role names with a leading hyphen, trailing hyphen, or consecutive hyphens are refused at spawn.

## Ticket runs
A ticket run implements `/to-tickets` slices in parallel — one sonnet implementer per runnable slice, each in its own worktree — and lands every slice on the branch the run started from, one `Slice NN:` commit each. It is the parallel counterpart of `/run-afk` and uses its tickets and tracker tools, so either can pick up where the other stopped. Step 0 applies unchanged (init, reap, lead title, `<lead>`); a ticket run needs a git repo.

**T1. Tickets.** If the tracker already holds the feature's tickets (`--tickets [slug]`, or the task names them), go to T2. Otherwise build them with the user first: run step 1 (grill the task with `grill-with-docs`), then invoke `to-spec` (it publishes the spec) and `to-tickets` (it quizzes the user on the breakdown and publishes the approved tickets). Both need the tracker that `/setup-matt-pocock-skills` configures; if `docs/agents/issue-tracker.md` is missing, ask the user to run it first.

**T2. Approve the queue.** Run `bash ~/.claude/skills/team/team.sh tickets --dry-run [--slug <slug>] <team>`: it lists the slices runnable now (blockers done, no file or Databricks-bundle overlap) and names the branch and start commit. Exit 2 = uncommitted changes, a detached HEAD or several features (pass `--slug`) — tell the user. Show the queue and use AskUserQuestion with first option "Implement these in parallel (Recommended)". Say that slices land on the named branch as they finish, that implementers run in auto permission mode, and, in GitHub mode, that each landed slice closes its issue.

**T3. Claim and spawn.** Run `bash ~/.claude/skills/team/team.sh tickets [--max N] <team>` (`--roles N` from the user becomes `--max N`; default: every runnable slice, up to the 8-teammate cap). For each `claimed<TAB><slice><TAB><role><TAB><title><TAB><ticket>` line: append `- [ ] <team>-<role>: slice <slice> <title> — owns: the slice — model: <sonnet id> — spec: run-afk Part B` to `<run>/tasks.md`, write the implementer prompt below to `<run>/prompts/<role>.md`, and run `bash ~/.claude/skills/team/team.sh spawn --worktree <team> <role> <run>/prompts/<role>.md <sonnet id>` (no gate: slices land locally). Then the monitor as in step 3. The implementer prompt carries step 3's instructions (lead name, subagents, facts, status line) with the report format replaced by this:
- "You are `<team>-<role>`, the implementer of slice <slice> (<title>), tracker mode <mode>, slug <slug>. Ticket: <ticket>. Main checkout: <root>. Your worktree: `<root>/.team/worktrees/<team>-<role>` on branch `team/<team>-<role>` — edit and commit only there. Read `~/.claude/skills/run-afk/SKILL.md` and run its **Part B (B1–B8) for this slice only**, with these overrides. Read the ticket, the spec, CLAUDE.md, the glossary and `docs/adr/` at their main-checkout paths. Run every `tracker.py`/`progress.py` command from the main checkout (`cd <root> && python3 ~/.claude/skills/run-afk/ralph/lib/<tool> ... --slug <slug>`), and never edit or commit `.scratch/` in your worktree: the lead owns tracker state. B7: do not tick criteria, mark the slice done, hand it off or close its issue — the lead does that when it lands your commit; for a partial slice, `tracker.py comment` what is done and what is left. B8: one commit, subject `Slice <slice>: <short title>`; never push or merge. A question goes to the lead as `NEEDS INPUT`; end as needs-human only for Part B's hard rules (destructive prerequisite, ADR conflict, the give-up rule). Other implementers work on other slices at the same time. When done, write the B9 block followed by a `PARALLELISM:` line to `<run>/reports/<role>.md`, tick your line in `<run>/tasks.md`, then SendMessage the B9 block to `<lead>` as your last act."

**T4. Land each slice as it reports.** Check the B9 block against its worktree (a `Slice <slice>:` commit on its branch, nothing uncommitted), then `team.sh finish <team> <role>` and act on its status:
- `done` → `bash ~/.claude/skills/team/team.sh integrate <team> <role>`. It rebases the slice onto the branch, fast-forwards it and marks the slice done. When it says it rebased over newer commits, run the project's feedback loops (CLAUDE.md, run-afk B5) on the main checkout; if they fail, resume the implementer (`spawn --resume`) with the failure, telling it to `git reset --hard <branch>` in its worktree and fix forward in a new `Slice <slice>: fix …` commit, then finish and integrate again. Exit 5 (rebase conflict, nothing changed) → resume it with the listed files: rebase onto `<branch>` in its worktree (the `resolving-merge-conflicts` skill), rerun its loops, report again. Exit 2 → read why and fix the precondition; never commit the user's own changes.
- `partial` → `team.sh tickets --release <slice> <team>`, so the slice can be claimed again; a second `partial` for the same slice in this run counts as needs-human.
- `needs-human` → `cd <root> && python3 ~/.claude/skills/run-afk/ralph/lib/tracker.py handoff <slice> --reason "<what the human must do>" --mode local --slug <slug>` (GitHub: `--mode github`), and relay the reason to the user.
Then refill: run `team.sh tickets <team>` again — a landed slice unblocks its dependents — and spawn whatever it claims. Repeat until it prints `tickets: queue empty`, or until nothing is runnable and no implementer is live; then list the slices still open with what blocks them, and the ready-for-human ones.

**T5. Review the result (opus).** When the queue is done, spawn two opus teammates — a reviewer and a skeptic (saved roles if they exist) — on `git diff <start commit>..<branch>` (start commit from the `tickets:` line), read-only, with the spec as their brief. Run one challenge round (step 4), then synthesize and record (step 5): what landed (each slice, its commit), Consensus, Disputed, Dropped, Next steps. A fix the review agrees on becomes a new ticket (`to-tickets`) for a follow-up ticket run, not an edit by the lead. Shut down as in step 5; `team.sh clean <team>` removes the implementers' worktrees (their branches stay).

## --inline mode
Steps 1–2 (understand the task, get the plan approved) apply unchanged. Skip `team.sh spawn`/`close` (still run `init`); no worktrees or gate — inline teammates share your working tree, so give editing roles exclusive files. Spawn all teammates in one message with the Agent tool (`name: <role>`, `model` if given), same prompts minus the pane/ListAgents lines; their reports return to you automatically (write them to `<run>/reports/` yourself). Challenge rounds use SendMessage `to: <role>`. No panes to clean up. The monitor is skipped under `--inline` (requires cmux and a registry, neither exists here); track inline teammates by the reports they return to you and by `tasks.md`.
